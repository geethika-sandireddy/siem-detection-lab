# T1053.005 — Scheduled Task/Job: Scheduled Task

**Victim:** Windows 10.

## Atomic test used

```powershell
Invoke-AtomicTest T1053.005 -TestNumbers 1
```

Creates a scheduled task via `schtasks.exe /Create` that runs a benign
command at a fixed time — the classic "run again after reboot" persistence
pattern.

```
Invoke-AtomicTest T1053.005 -TestNumbers 1 -Cleanup
```
was run afterward to remove the task.

## What showed up in Wazuh

Two log sources again:

- **Windows Security Event ID 4698** ("A scheduled task was created") —
  requires the "Audit Other Object Access Events" advanced audit policy to
  be enabled; off by default, so this had to be turned on explicitly via
  `auditpol.exe`.
- **Sysmon Event ID 1** — `schtasks.exe` process creation with the full
  `/Create /TN ... /TR ...` command line, including the task's target
  command.

## Rule test result

| Rule | Fired? | Notes |
|------|--------|-------|
| `100030` (Event 4698) | ✅ | Fired, but only after enabling the advanced audit subcategory — off by default, easy to miss in a real deployment |
| `100031` (schtasks.exe cmdline) | ✅ | Fired, redundant confirmation via Sysmon |
| `100032` (user-writable path heuristic) | ❌ (expected) | Atomic's test task points at `C:\Windows\System32\...`, not a user-writable path — rule correctly stayed quiet since this wasn't actually the persistence pattern it targets |

**Verdict: caught, with a real-world catch.** The most important finding
here isn't the rule firing — it's that **4698 auditing is off by default**
on a stock Windows install. A lab that only tested "does my rule work" and
never checked the audit policy prerequisite would have shipped a rule that
looks correct but silently never fires in production.
