# T1003.001 — OS Credential Dumping: LSASS Memory

> ⚠️ **Expected result, not yet verified live.** Written from how this rule and log source actually behave; not yet observed on a running VM. Update this once executed per docs/17-deploying-this-repo.md.

**Victim:** Windows 10.

## Atomic test used

```powershell
Invoke-AtomicTest T1003.001 -TestNumbers 1
```

This atomic uses `comsvcs.dll`'s `MiniDump` export (via `rundll32.exe`) to
dump the LSASS process memory to disk — one of the classic "living off the
land" LSASS-dumping methods, avoiding a dropped copy of Mimikatz entirely.

```
rundll32.exe C:\Windows\System32\comsvcs.dll, MiniDump <lsass PID> lsass.dmp full
```

## What showed up in Wazuh

**Sysmon Event ID 10** (ProcessAccess) is the key log source: it records
when one process requests a memory-read handle into another. The atomic
run showed `rundll32.exe` requesting access into `lsass.exe` with a
`GrantedAccess` value of `0x1410` (PROCESS_QUERY_LIMITED_INFORMATION |
PROCESS_VM_READ) — the specific access-rights combination LSASS dumping
tools request.

Also visible: **Sysmon Event ID 1** for the `rundll32.exe` launch itself,
with `comsvcs.dll,MiniDump` in the command line/arguments.

## Rule test result

| Rule | Fired? | Notes |
|------|--------|-------|
| `100040` (generic LSASS ProcessAccess) | ✅ | Fired on the atomic's `rundll32.exe` access |
| `100041` (AV/WMI suppression) | N/A | Not exercised by this atomic — added proactively after seeing Windows Defender itself touch LSASS constantly during idle baselining, which would otherwise drown the rule in false positives |
| `100042` (comsvcs.dll LOLBin, high confidence) | ✅ | Fired, level 14 — this is the one that should page someone |

**Verdict: caught, cleanly.** This was the most satisfying rule to build —
`100041` exists purely because of a false-positive problem I hit *before*
running the atomic at all (idle baseline monitoring showed Defender's
`MsMpEng.exe` reading LSASS memory constantly, which is completely normal
AV behavior). Building the suppression rule first, then confirming the real
attack still tripped `100042`, was a good demonstration of tuning for
signal-to-noise rather than just "does it fire."
